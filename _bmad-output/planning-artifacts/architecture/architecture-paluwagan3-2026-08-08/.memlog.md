- (research) Soroban storage has three durabilities: persistent (archived on TTL expiry, restorable), instance (shares contract TTL, small, read every invocation), temporary (DELETED FOREVER on expiry, no archival)
- (research) CRITICAL Soroban semantic with no EVM analogue: "it is unsafe to rely on an entry expiring as it can be extended by anyone" — expiry can never be used as a deadline or state-transition mechanism, which directly threatens any naive implementation of round boundaries and the 48h grace window
- (decision by user) AD-3 storage policy: all value-bearing state persistent, TTL extended on every write; temporary storage forbidden for anything affecting member funds
- (question) residual from AD-3: a stalled Room stops being kept alive because nothing writes to it; a permissionless extend_room_ttl is the cheap fix — deferred, revisit before mainnet pilot

- (decision by user) AD-5 resolves it: score committed to Registry at join and immutable for that Room's duration; the Room contract computes ordering itself at start; no off-chain component ever submits an ordering; member sees their committed score before funds move
- (decision by user) AD-2 topology: Registry (network-wide) + Factory + one deployed Room instance per Room — funds physically isolated per Room, chosen deliberately because audit budget is thin and isolation bounds what a missed bug can cost
