# Story 1.1: Project scaffold with generated contract bindings

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a developer on Pal3,
I want the repository scaffolded to the architecture's source tree with a working contract build and binding generation,
so that every subsequent story starts from a layout and toolchain that cannot drift from the contracts.

## Acceptance Criteria

**AC-1 — Source tree matches the Architecture Spine exactly**

**Given** an empty repository
**When** the scaffold is created
**Then** the tree contains `contracts/` (`registry`, `factory`, `room`, `shared`), `services/` (`trust`, `kyc`, `indexer`, `rates`, `api`), `app/`, `shared/`, and `bindings/` exactly as the Architecture Spine specifies
**And** `app/` is scaffolded as React + Vite with `vite-plugin-pwa` supplying the service worker and manifest, and `shared/` holds the single implementation of cross-cutting derivations consumed by both `app/` and `services/` (AR-26 / AD-17)
**And** `contracts/shared` holds the Glossary-named common types and one `#[contracterror]` enum per contract with explicit stable discriminants (AR-16, AR-20).

**AC-2 — Contract workspace builds on the pinned toolchain**

**Given** the pinned toolchain
**When** the contract workspace builds
**Then** it builds with `soroban-sdk` 25.0.0 on Rust 1.84+ targeting `wasm32v1-none`
**And** the installed `stellar-cli`, `@stellar/stellar-sdk`, and Stellar Wallets Kit versions are recorded in the repository (AR-8, Stack table).

**AC-3 — Bindings are generated by the build, never by hand**

**Given** a successful contract build
**When** the build completes
**Then** TypeScript clients are regenerated into `bindings/` by `stellar contract bindings` as part of the build, not as a manual step
**And** `bindings/` is marked generated and excluded from hand-editing by lint or CI check (AR-8).

**AC-4 — No contract address or passphrase literal in source**

**Given** any service or client source file
**When** it is inspected for configuration
**Then** contract addresses and the network passphrase are read from environment at build/deploy time
**And** no contract address or passphrase literal appears in source (AR-23).

**AC-5 — Apache 2.0 from first commit**

**Given** the contract source
**When** the repository is published
**Then** every crate under `contracts/` carries an Apache 2.0 licence header and the repository carries the Apache 2.0 licence file (AR-12, NFR-9).

## Dev Notes

### Scope boundary — read this first

This is a **scaffold-from-toolchain story, not a template-clone story**. The architecture specifies no greenfield starter template ([epics.md § Additional Requirements](_bmad-output/planning-artifacts/epics.md)).

**In scope:** directory layout, build wiring, binding generation, config plumbing, licensing, version pinning.

**Out of scope — do not build these here:**

- Any contract *behaviour* — escrow, stakes, waterfall, ordering. Stub entry points only.
- The test harness, CI pipeline, and integration-test fixtures — **Story 1.2** owns all of it.
- Design tokens and the PWA visual shell — **Story 1.3** owns them. Task 3 adds `vite-plugin-pwa` and a working service worker; it does not style anything.
- The handle derivation function — `shared/` is created as its future home; the implementation lands with the Members surface.
- Playwright or any E2E framework. A framework-setup pass was deliberately halted pending this scaffold; it belongs with Story 1.2.

### Architecture constraints binding this story

| Rule | Requirement | Consequence if violated |
|---|---|---|
| **AR-8 / AD-8** | TypeScript clients generated by `stellar contract bindings` as part of the build. Hand-written encoding of contract types is prohibited; `bindings/` is never hand-edited. | Client and contracts drift in type shape — a defect class that stays silent until it moves money |
| **AR-16** | Contract types and functions use PRD Glossary terms verbatim | A synonym in code is a defect, not a style choice |
| **AR-17** | All amounts are integer stroops (`i128`). No floating point in contracts or services. Amounts are never formatted for display below the client layer | Rounding drift in money |
| **AR-18** | Ledger timestamp (seconds) is the sole time source in contracts. Contracts never receive a client-supplied time | Time becomes manipulable and untestable |
| **AR-20** | One `#[contracterror]` enum per contract, explicit stable discriminants, never renumbered once deployed. Clients map codes to copy and never parse messages | Deployed clients mis-map errors after a renumber |
| **AR-23** | Contract addresses and network passphrase come from environment at build/deploy; never hard-coded | Wrong-network deploys; secrets in git history |
| **AR-12 / NFR-9** | Apache 2.0 from first deployment — chosen over MIT for the explicit patent grant | Members are asked to escrow money in code they cannot inspect |
| **AD-17** | Cross-cutting derivations live in exactly one shared module consumed by `app/` and `services/` alike | Two conforming implementations still produce two names for one person |

### Source tree (create exactly this)

```text
pal3/
  contracts/
    registry/        # attestations, trust scores — network-wide
    factory/         # room deployment, capacity + backstop gates
    room/            # escrow, stakes, schedule, waterfall, payout
    shared/          # common types, error enums, glossary-named structs
  services/
    trust/           # score computation from chain events; commits to Registry
    kyc/             # provider webhook -> attestation issuance
    indexer/         # chain events -> read models
    rates/           # cached USD/PHP rate + source and timestamp; presentational only
    api/             # read-only query surface for the client
  app/               # mobile-first PWA — React + Vite, WalletConnect
  shared/            # the single implementation of cross-cutting derivations (AD-17)
  bindings/          # GENERATED TypeScript contract clients — never hand-edited
```

**Note on `services/rates`:** the AR preamble in `epics.md` lists services as "(trust, kyc, indexer, api)", omitting `rates`. That is a transcription slip in the preamble. Both the Architecture Spine's source tree and this story's AC-1 include `rates`. **Create `services/rates`.**

### Toolchain — verified against current sources (2026-08-13)

| Component | Use | Notes |
|---|---|---|
| `soroban-sdk` | **25.0.0** — as pinned by the spine | Current published stable is 25.1.1. The spine pins 25.0.0 and the spine is authoritative; build on 25.0.0. Moving to 25.1.1 is a spine amendment, not a dev decision. Flag it if 25.0.0 proves unavailable |
| Rust | 1.84+ | soroban-sdk 25.x declares MSRV 1.84.0 |
| Target | `wasm32v1-none` | The only wasm target the Soroban runtime supports |
| `stellar-cli` | Pin at install; v23.4.0 was recent as of mid-2026 | Provides `contract build` and `contract bindings` |
| `@creit.tech/stellar-wallets-kit` | Pin at install | **Caution:** 2.0.1 published within hours of this story being written. Verify stability before pinning, and re-confirm at the pinned version that the WalletConnect module still exposes `signXDR`/`signAndSubmitXDR` but **not** `signAuthEntry` — AD-15 and the whole entry-point design depend on that fact. Import path: `@creit.tech/stellar-wallets-kit/modules/walletconnect.module` |
| `vite-plugin-pwa` | 1.3.0 current | Requires Vite 5+; React virtual module is `virtual:pwa-register/react` |
| `@stellar/stellar-sdk` | Pin at install | Generated bindings depend on it; keep the version consistent with the `stellar-cli` that generated them |

**Critical build gotcha:** do **not** build with `cargo build --target wasm32-unknown-unknown`. That target is unsupported from Rust 1.82 onward — those versions enable wasm features (reference-types, multi-value) the Soroban environment rejects. Use `stellar contract build`, which targets `wasm32v1-none` and applies the runtime's required settings.

### Testing requirements for this story

Story 1.2 owns the harness. This story's verification is limited to:

- Clean-checkout build succeeds
- Binding regeneration is idempotent (second run produces zero diff) — this is the AR-8 guarantee and the check Story 1.2 will promote into CI
- `tsc --noEmit` passes across all TypeScript packages **against the generated bindings**, not against hand-written types
- Config and licence checks pass

Do not add contract unit tests here beyond whatever a stub needs to compile. Do not add Playwright, Vitest suites, or fixtures.

**Leave these seams for Story 1.2** — the harness needs them and retrofitting is expensive:

- Contract crates carry `soroban-sdk` with the `testutils` feature in `[dev-dependencies]` from the start
- The binding-drift check exists as a runnable script so CI can call it rather than reimplement it
- Keep the workspace layout flat enough that `cargo test --workspace` will reach every contract crate

### Risk context from test design

Three findings from `test-design-architecture.md` touch this scaffold:

- **R-007 (score 6)** — an entry point that requires detached auth or multi-party authorization violates AD-15 and puts the mobile surface outside the Wallets Kit. When stubbing entry points, give each a single `require_auth` on the transaction source. Story 1.2 adds the static CI check.
- **R-005 (score 6)** — no personal data on-chain. When defining Registry types in `contracts/shared`, the attestation carries an **opaque provider reference string only** — never a hash or derivation of an identity document (AR-19, AR-10).
- **R-009 (score 6)** — Stake rounding is unspecified in FR-13. Not resolvable here, but define monetary fields as `i128` so the eventual decision has an integer domain to land in.

### Project Structure Notes

- The repository currently contains only planning artifacts (`_bmad/`, `_bmad-output/`, empty `docs/` and `design-artifacts/`). There is no code and no manifest of any kind — this story creates the first.
- Do not disturb `_bmad/` or `_bmad-output/`. Add them to `.gitignore` only if the team decides to; they are currently committed and that is deliberate.
- The spine names PostgreSQL for read models as an `[ASSUMPTION]` — do not scaffold a database, migration tool, or ORM in this story. `services/indexer` and `services/api` are placeholder packages only.
- Hosting and deployment topology are explicitly Deferred in the spine. No Dockerfiles, no IaC, no deploy config.
